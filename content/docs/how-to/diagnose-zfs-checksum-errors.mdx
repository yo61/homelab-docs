title: Diagnose ZFS checksum errors
description: Work out what a CKSUM count on nas1 actually means, find which files are damaged when zpool status -v refuses to list them, and decide how to repair
---

import { Callout } from 'fumadocs-ui/components/callout';

`zpool status` reports data corruption in a way that consistently reads as worse than it is.
This page covers how to turn a scary-looking `CKSUM` count into a concrete list of damaged
files and a measured byte count, so the repair decision is made on evidence rather than on
the tone of the status output.

The worked example throughout is the real incident on `nas1` in August 2026, where a status
output implying total pool loss turned out to be **384 KiB** of damage.

## 1. Read the counters correctly

A typical alarming output:

```
        NAME                                      STATE     READ WRITE CKSUM
        TimeMachine                               ONLINE       0     0     0
          mirror-0                                ONLINE       0     0     0
            d098a203-3fcb-4743-9b76-babdf7044669  ONLINE       0     0 20.7K
            d2101320-ecbf-47d4-96e4-6cd7c198aca1  ONLINE       0     0 20.7K

errors: 8 data errors, use '-v' for a list
```

Three things to understand before doing anything:

**`CKSUM` counts failed read attempts, not damaged blocks.** A client that retries hard on
`EIO` inflates it without limit. On `nas1`, 20,293 checksum errors were **three** damaged
blocks read roughly 6,760 times each — macOS Time Machine retrying about 38 times per block
per hourly backup pass. The counter says nothing about how much data is affected.

**`READ 0 / WRITE 0` means the disks are fine.** Every I/O completed and was acknowledged.
Corruption that arrives with a valid SATA CRC was wrong *before* the CRC was computed, so
it is not a cable, a link, or a failing drive. A flaky cable shows up as `UDMA_CRC_Error_Count`
in SMART and `hard resetting link` in `dmesg`, and produces **READ** errors, not silent
checksum failures.

**Identical counts on both mirror members is the diagnostic signal.** When a block fails
checksum, ZFS tries the other member; if that one is good it repairs and increments only the
failing vdev. Equal counters plus `scrub repaired 0B` means every failure incremented both —
each bad block was bad on both disks. That is corruption on a path *shared* by both members,
after ZFS computed the checksum in RAM and before the bits reached two independent platters.

The only number that bounds the damage is the **`N data errors`** line, and even that
overstates it: the error log counts `(dataset, object)` pairs, so one damaged file appears
once for the live dataset and once more for every snapshot still referencing it.

## 2. Find which files are damaged

`zpool status -v` should list them, but on `nas1` it fails:

```
errors: List of errors unavailable: no such pool or dataset
```

<Callout type="info">
  Check whether this is really a failure. Run as a non-root user it says
  `permission denied` instead, which is a different problem entirely. Only
  `no such pool or dataset` is a genuine `ENOENT` from the kernel.
</Callout>

The listing is all-or-nothing, so a single unresolvable entry hides every error. With the
`head_errlog` feature active and a Time Machine share whose `aapltm-` snapshots macOS creates
and destroys continuously, unresolvable entries are close to inevitable.

You do not need that listing. The kernel still reports the object identifiers in the raw
event stream, and **ZFS object numbers are inode numbers**, so you can resolve them yourself.

### Collect the object identifiers

Each ereport carries a `zio_objset` and a `zio_object`, and **the two are only meaningful as a
pair**. Extract them per event rather than as two independent lists:

```bash
sudo zpool events -v | awk '
  /ereport\.fs\.zfs\./ { if (os && ob) print os, ob; os = ob = "" }
  $1 == "zio_objset"   { os = $3 }
  $1 == "zio_object"   { ob = $3 }
  END                  { if (os && ob) print os, ob }
' | sort -u | while read -r os ob; do
  printf 'objset=%s (%d)  object=%s (%d)\n' "$os" "$((os))" "$ob" "$((ob))"
done
```

```
objset=0x183 (387)  object=0x10e6 (4326)
objset=0x183 (387)  object=0x18c2 (6338)
objset=0x183 (387)  object=0x1fa1 (8097)
```

<Callout type="warn">
  Do not flatten this with something like `grep -E "zio_objset|zio_object" | sort -u`. That
  yields two unrelated sets and discards which object belongs to which dataset. The same object
  number can legitimately appear under several objsets, so a flattened list sends you searching
  the wrong mount and can pin an unrelated inode.
</Callout>

<Callout type="warn">
  The event ring buffer holds only 512 entries — a few hours on a busy pool. This gives you
  what was visible in that window, **not** a proven exhaustive list. A full scrub is what
  makes it exhaustive.
</Callout>

### Map the objset to a dataset

`zfs` exposes `objsetid` as a property, so no `zdb` is required:

```bash
zfs list -H -t all -r -o objsetid,name TimeMachine | awk '$1 == 387'
```

```
387     TimeMachine/robin
```

If the objset resolves to a live dataset, the damage is in live data. If it does not appear
at all, the entry refers to a destroyed snapshot — which is what breaks the `zpool status -v`
listing.

### Resolve each object number to a path

Search **the mountpoint of the dataset that object's own objset resolved to** — not whichever
dataset happens to be to hand:

```bash
find /mnt/TimeMachine/robin -inum 6338 -printf '%p  size=%s  mtime=%TF %TT\n'
```

```
/mnt/TimeMachine/robin/Robin’s MacBook Pro.sparsebundle/bands/162  size=3861540864  mtime=2026-08-25 22:29:58
```

To resolve several at once, pass each object number as its own `-inum` test:

```bash
find /mnt/TimeMachine/robin \( -inum 4326 -o -inum 6338 -o -inum 8097 \) \
  -printf '%i  %p\n'
```

## 3. Measure the real extent

Knowing the files is not the same as knowing the damage. Read each file in `recordsize`
chunks and record which offsets return `EIO`:

```python
import os, sys

CHUNK = 131072  # match the dataset recordsize

for path in sys.argv[1:]:
    size = os.path.getsize(path)
    fd = os.open(path, os.O_RDONLY)
    bad, off = [], 0
    while off < size:
        try:
            os.pread(fd, CHUNK, off)
        except OSError:
            if bad and bad[-1][1] == off:
                bad[-1][1] = off + CHUNK
            else:
                bad.append([off, off + CHUNK])
        off += CHUNK
    os.close(fd)
    total = sum(e - s for s, e in bad)
    print(f"{path}: {len(bad)} bad range(s), {total} bytes")
    for s, e in bad:
        print(f"    {s:,} .. {e:,}  ({s / size * 100:.1f}% into file)")
```

The shape of the result is itself diagnostic. **Isolated single records** point to a small
number of discrete past events. **Long contiguous runs** point to a single large event.
**Damage scattered broadly and growing between runs** points to something still active — stop
and investigate the write path before repairing anything.

On `nas1` this returned exactly one damaged 128 KiB record in each of three files: 384 KiB
total, against a status output recommending restoring the entire pool from backup.

## 4. Decide the repair

Both mirror copies are bad, so nothing can reconstruct the data. The choice is only about
what to put in its place.

**Recreate the dataset.** The honest option when the data matters. Destroy the affected
dataset and its snapshots and repopulate from source.

**Surgical overwrite.** Write zeros over the unreadable records. The damage becomes *known*
rather than *unreadable*, errors stop, and history is preserved. Reasonable when the damaged
extent is tiny and the content is reconstructible or disposable — a Time Machine sparsebundle
being the obvious case. Not reasonable when a silent hole would later be mistaken for real data.

<Callout type="warn">
  Gate the overwrite on a pre-flight check that every target is **currently unreadable**,
  **`recordsize`-aligned**, and **writable** — and abort if any target reads successfully.
  Without that gate a wrong offset destroys recoverable data.
</Callout>

Alignment is not optional. Writing a full `recordsize` record at a `recordsize`-aligned offset
replaces the whole record. A partial write forces ZFS to read the existing record first, which
returns `EIO`, and the write fails.

```python
fd = os.open(path, os.O_WRONLY)
os.pwrite(fd, b"\0" * CHUNK, offset)   # offset % CHUNK == 0
os.fsync(fd)
os.close(fd)
```

Pause any client writing to the files first.

### Clearing the error state afterwards

Repairing the live data does **not** clear `zpool status`, and neither does `zpool clear`.

`zpool clear` zeroes the per-vdev `READ`/`WRITE`/`CKSUM` counters, but the **persistent error
log survives it** — you will still see `N data errors` immediately afterwards. That log is only
rebuilt by a scrub, from whatever the scrub actually finds.

Which means a scrub run too early re-reports everything, because **every snapshot still
referencing the original bad blocks still contains them**. Overwriting the live records leaves
the snapshotted copies untouched.

To be genuinely rid of it, the snapshots holding those blocks must age out or be destroyed.
On a Time Machine share the `aapltm-` snapshots roll over on their own, so waiting is often
the cheapest option.

```bash
sudo zpool clear TimeMachine
sudo zpool scrub TimeMachine     # confirms whether anything remains
```

## 5. Contributory factors worth checking

Corruption on a shared path with healthy disks and no transport errors usually points at one
of these. None is proven for the `nas1` incident; they are the list worth walking.

- **Unclean shutdowns during writes.** Check `zpool history` for import frequency — repeated
  or clustered `zpool import` lines mean the box is restarting unexpectedly. `nas1` showed 12
  imports in three months, including one *during a scrub*.
- **UPS not actually monitoring.** `/etc/nut/` being populated proves nothing. `upsc -l`
  listing no UPS means nothing is being watched, and the TrueNAS **UPS** service may be
  `STOPPED` with `enable=False`.
- **RAM.** Check `dmidecode -t memory` for `Error Correction Type`. `nas1` has ECC
  (`18KDF1G72AZ` Micron parts), which pushes bad memory well down the list. Note that EDAC may
  register no memory controller, in which case ECC works in hardware but corrected-error counts
  are invisible.
- **Controller.** Map every disk to its controller with
  `readlink -f /sys/block/sd*` and compare which pools are affected. A correlation is
  suggestive but usually confounded with disk batch and workload — and an absence of ATA errors
  in `dmesg` argues strongly against the controller regardless.

## TrueNAS 26.0.0-BETA.3 gotchas

Three separate defects in this build interact badly with a pool in an error state.

**The error log listing fails.** `zpool status -v` returns `no such pool or dataset` instead of
listing damaged files, as covered above.

**The middleware reports the pool `OFFLINE`.** `pool.query` returns `status: OFFLINE`,
`topology: None` and nulls for every size, scan and fragmentation field, while ZFS itself
reports the pool `ONLINE` and serving data. It raises a matching alert,
`Pool <name> state is OFFLINE`. The GUIDs match, so it is not a stale database record.

The chain, which is worth knowing because the symptom looks nothing like the cause:

1. `truenas_pylibzfs` `pool.status()` reads the on-disk error log unconditionally and **raises**
   when it cannot resolve an entry. There is no way to skip it — `get_stats=False` does not
   help.
2. `query_impl()` in `plugins/zpool/query_impl.py` catches that in the **same handler** as
   `open_pool()`'s `EZFS_NOENT` and calls `continue`, silently dropping the pool.
3. `pool_normalize_info()` in `plugins/pool_/pool.py` gets an empty list back and returns its
   pre-built skeleton verbatim — which is where `status: 'OFFLINE'` and every null comes from.

The defect is the conflation. `EZFS_NOENT` from `open_pool()` means the pool is absent and
skipping it is correct; `EZFS_NOENT` out of `pool.status()` means the pool exists and is
healthy but one error-log entry points at a destroyed dataset. Callers cannot tell the two
apart because both arrive as an empty list.

<Callout type="info">
  Do not test this with `import libzfs` — that is the older py-libzfs and it reads the pool
  fine, which is misleading. Middleware uses **`truenas_pylibzfs`**, a different library.
  Reproduce with `truenas_pylibzfs.open_handle().open_pool(name=...).status(asdict=True)`.
</Callout>

**The storage dashboard then crashes** with
`Cannot read properties of null (reading 'class_special_usable')` — the UI dereferencing the
null topology `pool.query` handed it. It recovers once the error log empties, which needs a
scrub that finds nothing, which in turn needs the snapshots holding the bad blocks to be gone.
`zpool clear` alone will not do it.

<Callout type="warn">
  **SMART is absent from this build entirely.** There is no `smart` entry in the services
  list, and `smart.config`, `smart.test.query`, `smart.test.results` and
  `disk.smart_attributes` all return `Method does not exist`. Nothing runs scheduled tests or
  raises SMART alerts. Verify per-disk state directly with `smartctl -i /dev/sdX` — disks may
  report `SMART Disabled`, in which case enable it with `smartctl -s on /dev/sdX`.
</Callout>
