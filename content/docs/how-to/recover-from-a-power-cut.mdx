title: Recover from a power cut
description: Bring the homelab back after a power loss — unlock the OpenBao dataset, restart the app, and unseal the vault
---

import { Callout } from 'fumadocs-ui/components/callout';

When power returns, most of the homelab recovers on its own: the NAS (`nas1`) powers
back on and imports its pool, and the cluster nodes power on and Talos brings the
cluster back up.[^bios] The one part that needs a hand is **OpenBao** — its data
lives on an encrypted dataset that stays locked across a reboot, so you unlock the
dataset, (re-)start the OpenBao app, and unseal the vault.

Do the NAS steps through TrueNAS itself — the **web UI** (below), or equivalently
its CLI/API — never raw `zfs`/`docker` on the host, which bypasses the middleware and
desyncs its view of the app and dataset. Addresses and paths are in
[Environment](/reference/environment).

<Callout type="info">
  The cluster's control plane comes back and workloads that don't use NAS storage
  keep working **even while OpenBao is still sealed** — existing Kubernetes Secrets
  persist; only External Secrets Operator *refreshes* pause, and they resume on their
  own once you unseal, though [not instantly](#4-skip-the-wait-optional).
  **Workloads backed by
  a NAS PVC (Loki, Prometheus, Grafana, …) won't function until the NAS storage is
  available.** There's no rush on the unseal itself: let the cluster settle, then
  do the steps below.
</Callout>

## 1. Unlock the OpenBao dataset

OpenBao's data is on a **passphrase-encrypted** ZFS dataset (`space/apps/openbao`,
with children `config` and `data`). Passphrase encryption never auto-unlocks on
boot, so after a power event the dataset is locked and the app can't mount its
storage.

You'll know this is the problem when, in the TrueNAS UI:

- the **openbao** app shows **Crashed** and won't deploy — its logs show a mount
  failure under `/mnt/space/apps/openbao`;
- **Datasets → `space/apps/openbao`** shows **Locked**, with its children unmounted.

Unlock it from the web UI:

> **Datasets → `space/apps/openbao` → Unlock** → enter the **dataset passphrase** →
> tick **Unlock Children** → **Mount**.

The Datasets page then shows all three datasets unlocked and mounted.

<Callout type="warn">
  The **dataset passphrase** is a different secret from the OpenBao **unseal keys**
  — you need both (passphrase here, unseal keys in step 3). Unlock only through
  TrueNAS (web UI, or its CLI/API); the data is inside the locked dataset, so
  unlocking is the only fix — don't try to work around the mount error.
</Callout>

## 2. (Re-)start the OpenBao app

With the dataset unlocked, start the app from the web UI:

> **Apps → openbao → Start.**

Wait for it to show **Running**. OpenBao boots **sealed** — that's expected.

## 3. Unseal the vault

From wherever you have the `bao` CLI and the three unseal keys:

```bash
export BAO_ADDR=http://192.168.20.10:8200
bao status                 # reachable; Sealed = true
bao operator unseal        # run 3× — one unseal key each (threshold is 3)
bao status                 # Sealed = false
```

Unsealing is idempotent — a mistyped key just doesn't count toward the threshold;
rerun it. You don't *have* to touch ESO or Flux — once OpenBao is unsealed both
recover unattended — but after a long outage that lags the unseal by up to ~20
minutes, which looks a lot like being stuck. [Step 4](#4-skip-the-wait-optional)
explains why, and how to skip it.

## 4. Skip the wait (optional)

Everything here is a **shortcut, not a repair**. The cluster reaches the same state
on its own; these commands just stop you waiting for it, and let you confirm the
recovery now rather than watching `SecretSyncedError` for a quarter of an hour and
wondering what else is broken.

### ESO: store is `Valid` but the secrets aren't

The signature of a *successful* unseal that hasn't propagated yet is a healthy store
alongside failing secrets:

```bash
kubectl get clustersecretstore homelab-openbao   # Valid / True
kubectl get externalsecrets -A                   # SecretSyncedError
```

That pairing is expected and self-correcting, because ESO runs **two independent
reconcile loops on different clocks**. The store controller re-validates every ~7 min
and so recovers promptly; each ExternalSecret retries on controller-runtime's
exponential backoff, which **caps at ~16m40s**. After a multi-hour outage every
ExternalSecret has failed enough times to be pinned at that ceiling, so they trail the
store by up to ~17 minutes. The ExternalSecret events say
`ClusterSecretStore ... is not ready` even though the store now reports `Valid` — both
are true, they're just reading different moments.

Force every not-`Ready` ExternalSecret to re-read immediately:

```bash
kubectl get externalsecrets -A -o json \
  | jq -r '.items[]
           | select((.status.conditions[]? | select(.type=="Ready") | .status) != "True")
           | "\(.metadata.namespace) \(.metadata.name)"' \
  | while read -r ns name; do
      kubectl annotate externalsecret -n "$ns" "$name" \
        force-sync="$(date +%s)" --overwrite
    done
```

Or one at a time — the annotation just has to *change*, and `force-sync` is the name
ESO documents for this:

```bash
kubectl annotate externalsecret -n monitoring grafana-admin \
  force-sync="$(date +%s)" --overwrite
```

Each one syncs in a few seconds.

<Callout type="info">
  Restarting the operator (`kubectl rollout restart deploy -n external-secrets
  external-secrets`) also works, because the backoff state lives in an in-memory
  workqueue that a new pod starts fresh. It's the bigger hammer for the same nail —
  it drops the leader-election lease and re-reconciles all 11 secrets at once. The
  annotation is targeted and doesn't need it.
</Callout>

### Flux: `infra-secrets` failing its health check

`infra-secrets` runs with `wait: true` and a **5 m** timeout — shorter than ESO's
~16m40s backoff — so during any OpenBao outage it reliably logs:

```text
HealthCheckFailed  timeout waiting for: [ClusterSecretStore/homelab-openbao
status: 'InProgress', ExternalSecret/cert-manager/cloudflare-api-token status:
'InProgress', ...]
```

It has `retryInterval: 2m`, so it clears itself within a couple of minutes of the
ExternalSecrets going `SecretSynced` — you do not have to wait out its 1 h interval.
To take it immediately:

```bash
flux reconcile kustomization infra-secrets
flux get kustomizations              # all should reach Ready=True
```

<Callout type="warn">
  **Order matters — fix the ExternalSecrets first.** `infra-secrets` gates
  `infra-configs`, which gates `apps`. Reconciling it while its ExternalSecrets are
  still in backoff just fails the same 5 m health check again and holds that chain
  shut for another cycle.
</Callout>

## 5. Verify

```bash
kubectl get nodes                                 # all Ready
kubectl get clustersecretstore homelab-openbao    # Valid
kubectl get externalsecrets -A                    # SecretSynced
kubectl get storageclass                          # truenas-iscsi present
flux get kustomizations                           # all Ready=True
```

## 6. Ghost pods (normally already handled)

A node that stops running pods leaves **tombstone pods** behind: pod objects whose
controller has already replaced them, but which nothing ever deletes. They linger
in `kubectl get pods` looking like failures.

An hourly CronJob — `pod-tombstone-gc` in `kube-system`, defined in `flux-homelab`
— sweeps them up, so this clears itself within the hour and there's usually
**nothing to do here**. Read on if you don't want to wait, or want to check the
sweeper is earning its keep.

A node going away leaves tombstones in **two** different phases, and the
distinction matters because each needs a different filter:

| Phase | Left by | Shows as |
| --- | --- | --- |
| `Failed` | An **ungraceful** loss — a power cut. The kubelet gets no shutdown signal, so on reboot it marks the pods it *had* been running `Failed` rather than deleting them. | `ContainerStatusUnknown`, `Error`; reason `NodeShutdown` |
| `Succeeded` | An **orderly** shutdown — `talosctl reboot`, `talosctl upgrade`, a [`kubectl drain`](/how-to/drain-a-node). The containers are sent `SIGTERM`; one that handles it and exits 0 ends up here. | `Completed` |

<Callout type="info">
  Talos enables Kubernetes
  [Graceful Node Shutdown](https://www.talos.dev/latest/learn-more/knowledge-base/)
  by default (20 s regular / 10 s critical pods). That makes an orderly reboot
  *clean*, but it does **not** make it tombstone-free: it `SIGTERM`s the
  containers rather than deleting the pod objects, so a well-behaved container
  that exits 0 leaves a `Succeeded` pod behind. A power cut delivers no shutdown
  signal at all, so that handler never runs and no grace-period value can prevent
  it — the only thing that turns a power cut into an orderly shutdown is a UPS
  that signals the nodes before the battery dies.
</Callout>

Only **Deployment-managed** pods pile up. The DaemonSet and StatefulSet
controllers delete terminal pods and recreate them; the ReplicaSet controller
merely stops counting one as active and creates a replacement, leaving the
tombstone parented to a ReplicaSet that keeps it alive indefinitely. Kubernetes'
own pod GC is no help either: its `--terminated-pod-gc-threshold` defaults to
12500, a count a three-node cluster never reaches.

Find them:

```bash
kubectl get pods -A --field-selector status.phase=Failed        # power-cut ghosts
kubectl get pods -A --field-selector status.phase=Succeeded \
  -l pod-template-hash                                          # orderly-reboot ghosts
```

Clear them without waiting for the next sweep — these are exactly what the
CronJob runs:

```bash
kubectl delete pods -A --field-selector status.phase=Failed
kubectl delete pods -A --field-selector status.phase=Succeeded -l pod-template-hash
```

<Callout type="info">
  Use the **field selector**, not a name-grep: it's evaluated server-side and
  structurally can't match a `Running` pod, so it only ever removes tombstones.
  The `Succeeded` sweep needs the extra `-l pod-template-hash` because — unlike
  `Failed` — `Succeeded` is a perfectly normal resting state, for Job pods and for
  Last Light's sandbox pods. That label is set by the Deployment controller on
  ReplicaSet-managed pods and only those, so it spares both. Deleting a
  `Succeeded` Deployment pod is safe by construction: its `restartPolicy` is
  `Always`, so a container exiting 0 would be *restarted* rather than ending the
  pod — the only route to `Succeeded` is the kubelet ceasing to manage it.
</Callout>

<Callout type="warn">
  This clears *terminal* pods, not stuck `Terminating` ones. A stateful pod on a
  `truenas-iscsi` PVC can hang `Terminating` after a hard node loss because its
  `VolumeAttachment` never detached. That's a different fix (check
  `kubectl get volumeattachment`) — don't force-delete it, or the PVC may
  double-mount when it reschedules.
</Callout>

[^bios]:
    The nodes auto-power-on via their BIOS **Restore on AC Power Loss → Power On**
    setting. If a node doesn't come back after power returns, check that setting in
    its BIOS/UEFI.
