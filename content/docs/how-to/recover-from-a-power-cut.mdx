title: Recover from a power cut
description: Bring the homelab back after a power loss — unlock the OpenBao dataset, restart the app, and unseal the vault
---

import { Callout } from 'fumadocs-ui/components/callout';

When power returns, most of the homelab recovers on its own: the NAS (`nas1`) powers
back on and imports its pool, and the cluster nodes power on and Talos brings the
cluster back up.[^bios] The one part that needs a hand is **OpenBao** — its data
lives on an encrypted dataset that stays locked across a reboot, so you unlock the
dataset, (re-)start the OpenBao app, and unseal the vault.

Addresses and paths are in [Environment](/reference/environment).

<Callout type="info">
  The cluster comes back up and keeps working **even while OpenBao is still
  sealed** — existing Kubernetes Secrets persist; only External Secrets Operator
  *refreshes* pause. There's no rush: let the cluster settle, then do the OpenBao
  steps below.
</Callout>

## 1. Unlock the OpenBao dataset

OpenBao's data is on a **passphrase-encrypted** ZFS dataset (`space/apps/openbao`,
with children `config` and `data`). Passphrase encryption never auto-unlocks on
boot, so after a power event the dataset is locked and the app can't mount its
storage.

You'll know this is the problem when the OpenBao app won't start and you see any of:

- the app shown as **crashed** in the TrueNAS UI, or `Failed 'up' action for 'openbao'`;
- `docker ps -a` shows the `openbao` container stuck in **`Created`** with no logs;
- `docker start openbao` → `mkdir /mnt/space/apps/openbao/config: operation not permitted`;
- `zfs mount space/apps/openbao` → `encryption key not loaded`;
- `zfs list -o name,mounted -r space/apps/openbao` shows `mounted no`.

Unlock it in the **TrueNAS UI** (this keeps middleware's lock-state in sync, which a
raw `zfs load-key` does not):

> **Datasets → `space/apps/openbao` → Unlock** → enter the **dataset passphrase** →
> tick **Unlock Children** → **Mount**.

Confirm on the NAS:

```bash
zfs list -o name,mounted -r space/apps/openbao   # all three -> mounted yes
```

<Callout type="warn">
  The **dataset passphrase** is a different secret from the OpenBao **unseal keys**
  — you need both (passphrase here, unseal keys in step 3). Don't `mkdir` the
  mountpoint or `rm` anything to force the mount: the data is inside the locked
  dataset, and the only correct fix is to unlock it.
</Callout>

## 2. (Re-)start the OpenBao app

With the datasets mounted, start the app — TrueNAS **Apps → openbao → Start**, or
from the NAS shell:

```bash
docker start openbao
docker ps | grep -i bao        # STATUS now Up
```

OpenBao boots **sealed** — that's expected.

## 3. Unseal the vault

From wherever you have the `bao` CLI and the three unseal keys:

```bash
export BAO_ADDR=http://192.168.20.10:8200
bao status                 # reachable; Sealed = true
bao operator unseal        # run 3× — one unseal key each (threshold is 3)
bao status                 # Sealed = false
```

Unsealing is idempotent — a mistyped key just doesn't count toward the threshold;
rerun it. You don't need to touch ESO or Flux: once OpenBao is unsealed, ESO
re-reads the store on its next reconcile.

## 4. Verify

```bash
kubectl get nodes                                 # all Ready
kubectl get clustersecretstore homelab-openbao    # Valid
kubectl get externalsecrets -A                    # SecretSynced
kubectl get storageclass                          # truenas-iscsi present
```

[^bios]: The nodes auto-power-on via their BIOS **Restore on AC Power Loss → Power On** setting. If a node doesn't come back after power returns, check that setting in its BIOS/UEFI.
